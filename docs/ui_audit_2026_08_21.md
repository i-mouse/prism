## 2. Cardinality: chat → file

(a) Can one chat have multiple files?
Yes. The foreign key `file_records.chat_id` points to `prism_documents.chat_id`. There is no `UNIQUE` constraint on `chat_id` in `file_records`, only a standard index (`ix_file_records_chat_id`), meaning multiple files can share the same chat ID.

(b) Can one file belong to multiple chats?
No. The foreign key `ChatId` on the `FileRecord` entity is a singular, scalar value pointing to `PrismDocument`. A single file record points to exactly one chat.

(c) In practice today, does the upload flow create exactly one file per chat?
No, the frontend allows selecting multiple files, and the `SubmitPaperEndPoint` loops over `request.Files` and adds multiple file records to the same chat within a single request. 

Code (`SubmitPaperEndPoint.cs:106-136`):

  - `fetch('/api/chats/${activeChatId}/files')`: GET method. Fires when `activeChatId` changes, after fetching history, to backfill missed processing events.
  - `fetch('/api/chats/${userId}')`: GET method. Fires when `userId` changes (on load) to populate the sidebar.
  - `fetch('/api/papers')`: POST method. Fires when the user clicks "Upload & Analyze" (`handleUpload`).
  - `fetch('/api/chat/ask')`: POST method. Fires when the user submits a message (`handleSendMessage`).

- **Storage mechanisms:**
  - `activeChatId`: Kept in React state and synced to `sessionStorage` (wiped when tab closes).
  - `userId`: Hardcoded constant `demo-user-01`.
  - Uploaded files: Kept in memory via React state (`files`), sent in `FormData` via `fetch`.

- **SignalR setup:**
  - Setup: The `SignalRService` class wraps the connection builder and connects to `/hubs/document` on initialization via `signalRService.start()`.
  - Event Handlers: Only one event handler is registered: `signalRService.on('DocumentProcessed', handleDocumentProcessed)`.

- **Current routing approach:**
  - State-driven conditional rendering. No router library is used. The UI swaps chat contexts entirely by changing the `activeChatId` state, which triggers a `useEffect` cascade to swap out data.

## 6. SignalR wiring

- **DocumentHub server code:**
```csharp
using Microsoft.AspNetCore.SignalR;

namespace Prism.ApiService.Hubs;

public interface IDocumentClient
{
    Task DocumentProcessed(object data);
}
public class DocumentHub: Hub<IDocumentClient>
{
    private readonly ILogger<DocumentHub> _logger;

    public DocumentHub(ILogger<DocumentHub> logger)
    {
        _logger = logger;
    }

    // Called by the client after connect/reconnect so broadcasts can target
    // a ChatId-scoped group instead of a single (potentially stale) ConnectionId.
    public async Task JoinChat(string chatId)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, $"chat-{chatId}");
        _logger.LogInformation("Connection {ConnectionId} joined group chat-{ChatId}", Context.ConnectionId, chatId);
    }

    public override Task OnConnectedAsync()
    {
        _logger.LogInformation("SignalR connection established: {ConnectionId}", Context.ConnectionId);
        return base.OnConnectedAsync();
    }

    public override Task OnDisconnectedAsync(Exception? exception)
    {
        _logger.LogInformation(exception, "SignalR connection closed: {ConnectionId}", Context.ConnectionId);
        return base.OnDisconnectedAsync(exception);
    }
}
```

- **SignalR calls from the frontend:**
  - `signalRService.start(baseUrl)`
  - `signalRService.on('DocumentProcessed', handleDocumentProcessed)`
  - `signalRService.joinChat(activeChatId)` -> invokes `this.connection.invoke('JoinChat', chatId)`

- **How chatId groups are joined + left:**
  - Joined: Client calls `signalRService.joinChat(activeChatId)` on active chat change or network reconnect. This triggers the Hub's `JoinChat` method which calls `Groups.AddToGroupAsync(Context.ConnectionId, $"chat-{chatId}")`.
  - Left: Groups are never explicitly left by the client when navigating between chats. They are only left when the underlying connection disconnects entirely.

- **DocumentProcessed event payload:**
  - `status`: string (e.g., `'Completed'`, `'Error'`, `'Failed'`)
  - `fileName`: string
  - `summary`: string (contains either the successful summary or the error message)

## 8. Existing patterns to match

- **Error responses:** Methods return typed `Results` utilities, specifically `Results.Problem(...)`, `Results.BadRequest(...)`, and `Results.InternalServerError(ex.Message)`.
- **Postgres Database Access:** The DB is interacted with using standard EF Core inside endpoint delegates. The `PrismDBContext` is injected directly into handlers (`PrismDBContext dbContext`) and interacted with using standard `.Add()`, `.Where()`, `.FirstOrDefaultAsync()`, and `await dbContext.SaveChangesAsync()`. No Repository or MediatR patterns are used.
- **Async Handling:** Endpoints use native C# `async Task` or `async (...) =>` syntax with `await`.
- **Naming conventions:**
  - DTOs end in `...Request` or `...Response` (e.g. `ChatRequest`).
  - Route handlers reside in static classes ending in `...EndPoint` (e.g., `ChatEndPoint`, `SubmitPaperEndpoint`).
  - Entities use standard PascalCase naming conventions (e.g., `DocumentExtractor`).
- **Owned-entity / jsonb mapping:** 
  - `[Column(TypeName = "jsonb")]` attributes are heavily used in entity definitions (e.g., `Domain.cs`, `DocumentExtractor.cs`).
  - Enums map to strings explicitly using `.HasConversion<string>()`.
  - Complex properties in EF use `.OwnsMany(...)` combined with `.ToJson()` to serialize inline collections (seen in `PrismDBContext.cs:70` for `EvidenceSpans`).

## 9. Gaps flagged

- **Inconsistent Default Timestamps:** `PrismDocument.cs` uses `DateTime.Now` as its property default while everything else uses `DateTime.UtcNow`. This could lead to time-zone mix-ups in Postgres.
- **SignalR Group Leaks:** The frontend joins SignalR groups for `chat-{chatId}` when the active chat changes, but it never explicitly leaves the previous group. This could cause the client to receive unintended processing events if they navigate away from an ongoing upload.
- **Typo in Class Name vs Filename:** `SubmitPaperEndPoint.cs` contains the class `SubmitPaperEndpoint` (lowercase 'p' in Endpoint).
- **Hardcoded Identifiers:** The `UserId` in the frontend is hardcoded directly to `"demo-user-01"`. Python writer explicitly hardcodes the `RESEARCH_PAPER_DOMAIN_ID`.
- **Upload Chat Title Assumption:** When uploading a batch of multiple files, `SubmitPaperEndPoint` sets the `ChatTitle` using `$"Chat: {file.FileName}"` based on the *first* file it loops over that doesn't yet exist in the DB, ignoring the others.
